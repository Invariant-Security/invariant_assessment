# invariant_assessment

Evaluates a target's collected system facts (`docker exec` or SSH) against
every implemented hardening check (compatible with the CIS Benchmarks for
Debian and Ubuntu). No Postgres access -- returns each check's own `check_id`
with status/evidence; `invariant_api` maps the id to the matching control to
build a `Finding`.

SSH targets: the host key is verified before any credential is sent. With
`host_key_type` + `host_key_fingerprint` (`SHA256:...`) the connection is
pinned and a different key gives HTTP 409 (`detail.code = host_key_mismatch`);
without them it is trust-on-first-use. Responses carry `host_key_observed`
and `host_key_verification` (`operator` | `first_use`). Password auth requires
a pin.

Extracted from the `Invariant-Security/Invariant` monolith
(`src/invariant/assessment/`) as part of its split into `invariant_*`
services. `evaluate()`/`evidence()` logic for every `Check` is ported
unchanged -- only the wiring around it (no more direct Postgres lookup,
exposed over HTTP instead of called in-process) changed.

## Endpoints

- `GET /healthz`
- `POST /assessment/run?target=<container-name>` -- one `docker exec`
  round trip, then every `CHECKS` entry evaluated against that snapshot.
  Returns `{"document": "...", "results": [{"check_id": "...", "status":
  "PASS"|"FAIL", "evidence": "..."}]}`.

## CLI: `invariant assess`

Same engine as the HTTP service, from a terminal (installed by `pip install .`).
Exactly one target per run:

```bash
invariant assess --docker <container> [--format json|table]
invariant assess --ssh user@host[:port] --key ~/.ssh/id_ed25519 --known-hosts ~/.ssh/known_hosts
invariant assess --ssh user@host --key KEY --host-key-fingerprint SHA256:...
invariant assess --local
```

- `--ssh` is key-only and **requires** `--known-hosts` or `--host-key-fingerprint`
  (no trust on first use; without either the exit code is 2). A mismatching
  host key aborts before the key is used (exit 3).
- `--local` runs the same fixed collection script as the other transports via
  `["/bin/sh", "-c", SCRIPT]` (no `shell=True`, nothing from the user is
  interpolated into the script).
- `--format json` is the HTTP `RunResponse` plus `invariant_version`,
  `catalog_version` (sha256 of `catalog.json`), `target`, `transport`,
  `started_at`/`finished_at` (UTC), `run_id` (`INVARIANT_RUN_ID`, else
  `BUILD_URL`, else `GITHUB_RUN_ID`, else null) and, for `--docker`,
  `image_digest` + `image_digest_kind` (`repo_digest` or `image_id`). Each
  result gets `effective_status`: the engine `status` (unchanged: PASS / FAIL /
  NOT_ASSESSED) or `NOT_APPLICABLE` (host-only check on `--docker`; or a
  `requires: sshd|sudo` check where package, binary and process are all proven
  absent -- an unreadable signal gives `NOT_ASSESSED`, never `NOT_APPLICABLE`).
- Exit codes: 0 = the assessment ran (even with FAIL); 2 = usage error;
  3 = transport (unreachable, auth, host key, missing container);
  4 = internal error (OS not detected/supported, missing or corrupt
  `catalog.json`, unexpected exception): a one-line message with the error
  type, no traceback unless `INVARIANT_DEBUG=1`. 1 is reserved for the future
  gate; `assess` never returns it.
- Privileges: the "is sshd/sudo running" signal reads only the executable of
  each process (`readlink /proc/<pid>/exe`; never cmdline or environ) and is
  reduced on the target to a yes/no -- the executable list is never returned,
  logged or printed. Reading other users' executables needs root or
  `CAP_SYS_PTRACE`. As a non-root user (`--local`, or `--ssh` with a user other
  than root) the CLI warns on stderr; if any executable is unreadable the
  process signal is unknown, so checks with `requires` can come out
  `NOT_ASSESSED` (and the future gate fails closed on that).
- `src/invariant_assessment/catalog.json` is generated by
  `invariant_api/scripts/export_check_catalog.py --out ...`; do not edit by hand.

## Image vulnerabilities (Trivy, INV-81)

`python -m invariant_assessment.vuln <image> | --docker <container>` lists the
CVEs of an **image** (for a container, the image ID it runs; never the running
container) with the embedded Trivy. Development entry point only: there is no
`invariant` subcommand, and `invariant assess` stays CIS-only. Output is JSON
(`findings` deduplicated by cve+package, `total_findings`, `unique_cves`,
`trivy_version`, `db_version`, `db_updated_at`, `image_ref`, `db_age_warning`);
`cvss_v3_score` (NVD first, else vendor) is informational only.

- The container image ships Trivy v0.76.1 (tarball SHA-256 pinned in the
  Dockerfile; the build fails on mismatch). With the pip install, `trivy` must
  be in `PATH`; if it is absent only this module fails, `invariant assess` is
  unaffected.
- Offline: the database lives in a directory given by `INVARIANT_TRIVY_CACHE`
  (a volume, **never inside the image**: ~1.6 GB). Prepare it once, and refresh it
  regularly, with the same directory:
  `trivy image --download-db-only --cache-dir $INVARIANT_TRIVY_CACHE` and
  `trivy image --download-java-db-only --cache-dir $INVARIANT_TRIVY_CACHE`.
  Scans run with `--skip-db-update --skip-java-db-update --offline-scan
  --cache-backend memory`, so the cache can be mounted **read-only** (`:ro`).
- DB age (`UpdatedAt`): over 3 days = warning on stderr and in the JSON; 7 days
  or more (vulnerability DB or Java DB) = exit 4. Limits:
  `INVARIANT_TRIVY_DB_WARN_DAYS` / `INVARIANT_TRIVY_DB_MAX_DAYS`.
- Exit 0 = ok, 2 = usage, 4 = any failure (Trivy missing or failing, invalid
  JSON, DB or Java DB missing or too old); never 0 on failure. Traceback only
  with `INVARIANT_DEBUG=1`.
- Trivy talks to the Docker socket to read the local image (the service already
  mounts it).
- Credits: see `NOTICE` (Trivy, Aqua Security, Apache 2.0).

## Locked dependencies

`requirements.lock` (hashed) is what the image and CI install; `pyproject.toml` keeps the loose ranges.
Regenerate (add/bump a dep): in `python:3.12.14-slim@<digest>`, `pip install pip-tools && pip-compile --generate-hashes --strip-extras --allow-unsafe -o requirements.lock` with the deps from `pyproject.toml` as input.
Bump the base: `docker buildx imagetools inspect python:3.12.14-slim` (or the new tag) → put the index `Digest:` in the Dockerfile `ARG BASE`, then rebuild and run `pip check`.
